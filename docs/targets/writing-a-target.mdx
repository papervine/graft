---
title: "Writing a target"
description: "The subprocess protocol for generating SDKs in any language."
---

A target is an **executable**, not a plugin. besdk hands it the IR as JSON on stdin and reads a file
manifest from stdout.

That boundary is the point: it lets a Go target be written *in Go*, using `go/ast` and `gofmt` —
the only realistic way to hit the quality bar for a language whose tooling lives in its own
ecosystem. A single-host-language plugin API would force every target author to hand-roll a printer
for a language they may not primarily write.

## The contract

<Steps>
  <Step title="Handshake">
    ```sh
    besdk-target-mylang --sdk-target-protocol
    ```

    ```json
    {
      "name": "mylang",
      "version": "0.1.0",
      "irVersions": ["1.x"],
      "capabilities": ["pagination", "read-write-split"],
      "displayName": "MyLang"
    }
    ```

    `irVersions` are semver ranges. besdk refuses to run a target whose range excludes the IR it
    produces — **an error, never a warning**, because a target reading an IR it does not understand
    produces a subtly wrong SDK, which is worse than no SDK.
  </Step>

  <Step title="Generate">
    ```sh
    echo "$IR_JSON" | besdk-target-mylang
    ```

    Input:

    ```json
    {
      "irVersion": "1.5.0",
      "ir": { "…": "…" },
      "options": { "packageName": "acme-sdk" },
      "brand": {
        "name": "besdk",
        "title": "besdk",
        "homepage": "https://github.com/besdk/besdk",
        "configFile": "besdk.yaml",
        "generatedNotice": "Code generated by besdk. DO NOT EDIT.",
        "attribution": "_Generated by [besdk](…). Edit the spec or `besdk.yaml`, not this package._"
      }
    }
    ```

    Output:

    ```json
    {
      "files": [{ "path": "src/client.go", "contents": "package …" }],
      "warnings": []
    }
    ```

    `options` is whatever `targets.<name>` held in `besdk.yaml`, passed through untouched — besdk
    never needs to know your target's settings.

    <Warning>
      Use `brand` for any attribution you emit. Never hardcode the generator's name: it appears in
      files your users commit, so a rename would break them. The strings are sent to you precisely so
      you do not have to know them.
    </Warning>
  </Step>
</Steps>

Anything on stderr is surfaced as log output. A non-zero exit, or stdout that fails to parse, is a
hard failure — never a partial write.

## Discovery

besdk looks for `besdk-target-<name>` on `PATH`. Blessed targets ship in-tree, and **get no shortcut
around this protocol** — the TypeScript target is spawned exactly as a third-party one would be,
because a plugin API that nothing external exercises rots.

## What the IR gives you

```sh
besdk ir openapi.yaml --config besdk.yaml > ir.json
```

That file is byte-for-byte what your target receives, so you can develop against it directly.

Highlights:

- `service` — name, `displayName` with the author's own casing, servers, auth schemes, constant headers
- `types` — deduplicated and topologically ordered; cycles flagged rather than inlined
- `resources` — a tree; `subresources` nest
- `errors` — the taxonomy, per status
- `pagination` — schemes referenced by method

**Names are token sequences**, never pre-cased: `{ "tokens": ["user", "id"] }`. Apply your own
convention — `userId`, `user_id`, `UserID`. A target that receives pre-cased names cannot be
idiomatic.

`role` on an object type (`read`, `create`, `update`, `shared`) tells you which side of a read/write
split it is, which is also what makes breaking-change classification possible.

**Server URLs arrive already resolved.** `server.url` never contains a `{placeholder}`, so a target
that ignores variables entirely still produces a working SDK. When the spec templated the URL, the
original is kept in `server.urlTemplate` alongside `server.variables` (each with a `default` and
sometimes an `enum`) — substitute into the template if you want to expose them as client options. See
[Server URLs](/guides/server-urls) for how the in-tree targets do it.

## Expectations

Targets are held to the same bar as the in-tree one:

- **Emit ASTs or a structured builder, not string templates.** Templates cannot manage imports or
  deduplicate types, which is why templated output reads dead.
- **Hand-write the runtime.** Transport, retries, auth, and pagination belong in a reviewed library
  vendored into the output — not generated per endpoint.
- **Declare your gates in the handshake**, and run nothing yourself. besdk executes them for you.
- **Build each file in one pass.** See below — this is worth more than it sounds.

## Declaring verification gates

Name your formatter and typechecker in the handshake; besdk runs them in the output directory, in order,
after writing.

```json
{
  "gates": [
    { "name": "gofmt", "command": ["gofmt", "-w", "."], "kind": "fix" },
    { "name": "go build", "command": ["go", "build", "./..."], "kind": "verify" }
  ]
}
```

| Field | Meaning |
|---|---|
| `kind: "fix"` | Run for side effects; the exit code is **ignored** |
| `kind: "verify"` | A non-zero exit fails generation |
| `optional: true` | A missing executable is a warning, not a failure |

The `fix`/`verify` split is not cosmetic. `ruff check --fix` exits non-zero when something remains it
could not fix — but the formatter has not run yet at that point, so its verdict is premature. Treating it
as one failed generation on a line the very next step would have wrapped. Every formatter has this shape.

Mark a formatter `optional`, never a typechecker: absent formatting is a cosmetic loss, absent
typechecking removes the guarantee the whole pipeline is premised on.

If your tool lives inside your own dependencies, emit an **absolute path** — you know where your
installation is and besdk does not.

<Warning>
  Declare gates. A target that declares none produces unverified output, and besdk will say so on every
  run. There is no built-in fallback for any language.
</Warning>

## Declaring capabilities

`capabilities` tells besdk what you implement, and `besdk targets` prints it. Declare what you actually
emit — no more, and no less. Under-declaring misleads anyone reading your target as an example;
over-declaring claims behaviour you do not have.

## Build the whole file, then hand it to the AST library once

Every serious AST library revalidates its model after a mutation, so a generator that mutates
per-declaration pays for that revalidation per declaration — on a file that is growing as it goes.

The in-tree TypeScript target learned this the expensive way. Emitting Stripe's SDK took **five and
a half minutes**, and a CPU profile put 81% of it in TypeScript's own scanner, JSDoc parser, and the
garbage collector feeding them — parsing text the generator had just written. The shape at fault
looks entirely reasonable:

```ts
// Quadratic: one reparse of the whole file per property.
const iface = file.addInterface({ name });
for (const field of fields) iface.addProperty({ ... });
```

```ts
// One parse for the file, byte-identical output.
file = project.createSourceFile(path, {
  statements: [...imports, { kind: StructureKind.Interface, name, properties }],
});
```

The same run now takes **2.3 seconds**. Assemble your file as data and create it once.

<Tip>
  Speed is not only a convenience. At five minutes a run, large specs get exercised once a session
  instead of on every change — and the large specs are where the interesting bugs are. Fast
  generation is what makes a broad corpus usable as a test suite.
</Tip>

<Warning>
  Manifest paths are validated: absolute paths and `..` segments are rejected. A target is
  third-party code, so its output is untrusted input.
</Warning>
