---
title: "Enrichment, not translation"
description: "Why real specs need more than translating, and what graft asks you for."
---

The premise behind `graft check` and `graft.yaml`:

> **Real specs are under-specified, not merely irregular.**

Translating an under-specified spec faithfully produces an SDK that compiles and is unpleasant. So
graft's job is not only to translate — it is to *enrich*.

## What that looks like in practice

From a real 121-operation spec:

| Property | Value |
|---|---|
| Named schemas declaring any `required` fields | 6 of 27 |
| Error responses declaring no schema | 182 of 186 |
| Declared response headers | 0 — the pagination total was described in prose |
| Schemas used as both request and response | 19 |

None of that is a malformed document. It parses, it validates, other tools accept it. It simply does
not say enough to build a good client from.

## Two consequences

**`graft.yaml` is a primary surface, not a patch kit.** Most of what makes output good on a real spec
is expressed there — which is why `graft init` writes a starting config rather than leaving you a
blank file.

**Under-specification is surfaced, never papered over.** A generator that quietly emits an
all-optional, error-untyped SDK has produced something that compiles and misleads. `graft check`
makes the invisible visible, with a config fragment for each finding:

```
⚠ 19 schemas serve as both request and response bodies.          [M001]
⚠ 182 of 186 error responses declare no schema.                   [E001]
⚠ 21 named schemas declare no required fields.                    [M002]
ℹ 14 operations accept paging parameters but do not appear to
    return a collection; not paginating them.                     [P002]
```

## What only you can answer

graft marks these `REVIEW` in the config it generates, because no amount of analysis can infer them:

**Which fields the server assigns.** Guessed from naming conventions, and usually right — but you
know. Getting it wrong leaves `_id` in your create model.

**Which fields are always present.** If your spec declares nothing `required`, every field is
optional and your users null-check everything. This is the single biggest quality lever you control.

**Whether an endpoint really paginates.** graft declines to paginate operations whose response does
not look like a collection, and lists them so you can correct it.

<Tip>
  You can also answer these in the spec itself with [`x-graft-*` extensions](/reference/extensions),
  which travel with your API instead of living in the generator's config.
</Tip>
